# HTTPS 发布与单二进制验收流程

这是一份可复用的操作流程，不含凭据或内部推理记录。

1. 先确认新仓库的名称和公开范围，再创建 public 仓库。
2. 在项目内设置 Git 身份：user.name=jacek4yang，user.email=jacek4yang@outlook.com。
   不修改其他电脑或全局 Git 配置。GitHub 连接器生成的提交可能采用账号显示名
   Jacek Yang；这与本地 git config 的姓名字段不同，需要如实区分。
3. 优先复用已连接的 GitHub 通道，通过 HTTPS 发布。普通快进更新即可时，
   不额外创建个人令牌，也不增加历史重写或临时导入工作流。
4. 在验证分支运行测试，确认上传树与本地已验证源码一致，不能只看“上传成功”。
5. 六个构建目标：Windows x86-64 静态 CRT；Linux x86-64 musl 静态版；Intel macOS x86-64；Apple Silicon macOS ARM64；Linux ARM64 musl 静态版；
   Linux x86-64 GNU 兼容版。每个目标只需要一个可执行文件即可运行。
6. 检查格式、Clippy、单元/性质/真实网络测试，实际测试剪贴板、杀进程恢复、
   完整校验和不覆盖已有文件。提示必须通过 Linux/macOS PTY / Windows ConPTY 的
真实按键验收，不能仅靠管道输入测试。不能跳过失败测试来获得绿色结果。
7. 检查 Windows PE 导入表，不允许额外 VC 运行库或应用 DLL；检查 musl ELF
   没有解释器和 NEEDED 动态库。许可证嵌入二进制，附带文档不属于运行依赖。
8. 验证分支通过后，合并经审查的 PR 到 main，并核对合并后的源码树和提交；
   如果源码有变化，必须重新验证。
9. GitHub Actions 在全部目标通过后，使用仅限发布任务的 contents:write 权限
   创建 Release、上传二进制压缩包与 SHA-256 校验文件。版本标签必须与 Cargo
   版本一致。仅发布用户明确批准的版本；本次候选为 v0.1.1 稳定版，
   不标记 Pre-release，不覆盖已有发布或标签。
10. 检查 Release 对应的提交、公开状态、附件数量与校验值，再通知发布成功。

clipx 不向磁盘保存设备身份、私钥、指纹或信任记录。核对后仅在当前进程内存
记住对方身份，退出即忘记。真实终端按 Y 直接确认，N/回车拒绝，Esc 取消。
--yes 只跳过当前进程的本端确认，接收端仅在 Downloads 保留必要断点，成功后清理。
不同系统和 CPU 架构必须使用对应构建。剪贴板受桌面协议和权限限制。

本流程不需要新增个人令牌时，不存在“本次新增授权”的撤销步骤。现有 GitHub
连接和用户其他设备保持原样。如果以后确实需要新凭据，先明确最小仓库范围、
用途、有效期和单独撤销方法，再请求许可。仅删除本地凭据不等于服务端撤销；
不要为了清理一次任务而撤销整个 GitHub CLI 应用的所有设备授权。
